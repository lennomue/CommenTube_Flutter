# 開発の計画

## 1. 事前情報
- `spec.md`,`spec_mock.md`
  ゲームの実装要件。一部データ型の設計などの細かい計画はデータベースとの相性などを考慮して適宜変更の提案をすること。ゲームの進行や通信のタイミングの設計についても改善の余地があれば提案してください。今の計画書にある骨格のコンセプトやゲームのユーザーの操作手順は変えずに、それを達成するための技術的な選定についてはより良い選択肢があれば変更してほしい。mock版はバックエンドサーバーを立てずに行う。

- `game_images`
  ゲームの画面構成の外観を画像で示す。基本的な画面構成はspec.mdに基づく。設計はできだけシンプルが良い。画像に示すような適度な光や影、透明感や立体感の実装は後回し。見た目のデザインよりも挙動、機能面のデザインを優先して実装すること。もしどうしても画像が必要な場合はassets/imagesフォルダなどを追加してください。画像の生成は禁止。追加する画像のサイズなどの条件の指示を出してください。

- `plan.md`
  現状での計画への理解が書かれている。当然より良い開発の道筋や変更すべき点があれば積極的に指摘してほしい。またデータベースの設計についてはあなたが触れる環境の中では解決しないものがあるだろうと思われる。その際にはその計画を実行するための手順を詳しく示してください。
  
- `_commit.md`
  コミットする毎に変更点を書き加える。コミットのタイミングはこちらから指示をするので、作業が一区切りしたタイミングで前回書いた時からの変更点を簡潔にAIが加筆する。

## 2. 開発の進行
- 前提や実装に際しての技術的課題に不明点があればわかったふりをすることなく確認すること。
- 実装に際して世の中ですでに使われているライブラリや設計方法を使い回すことができるかを調べ、それを実装すること。すでに`spec.md`にある計画でも、良い設計があれ積極的に変更して良いので提案すること。
- 開発初期にjsonデータで実装する時はその時点で必要最適源の簡潔なデータのみを扱うこと。
- コードを書く際には余計な実装をしないこと。もし進めたいことがあるならば事前に確認すること。
- コードの中で不要なものは消すこと。消さないならば残している理由（役割）をファイルの中にコメントなどで書くこと。
- GitHubに更新版をpushする際には変更内容を簡潔な箇条書きで`_commit.md`に加筆すること。
- CI/CDに注意して適切なテストができると良い。環境として容量が小さい現在のmacではFlutter SDKでコンパイルし、実機スマホに繋いでアプリのテストを行う。そのためAIエージェントがテストを行うのは難しいかもしれない。

## 3. 開発フェーズ

各フェーズの終わりには、そのフェーズの「成功基準」を満たしているかを確認してからコミットし、`_commit.md`に変更点を加筆する。AIエージェントはFlutterアプリを実機で動かして目視確認することができないため、実機での動作確認が必要な項目は人間が確認し、その結果をエージェントにフィードバックする運用とする。

### フェーズ0: 開発環境・雛形構築

ここはすでに実装が終わっている箇所に重なるかと思う。修正が難しければmy_test_appでなく、新しいプロジェクトとして初めからやり直そう。
**やること**
- `flutter create`でプロジェクトを作成し、以下を`pubspec.yaml`に追加する: `flutter_riverpod`, `go_router`, `drift`(+`drift_dev`, `sqlite3_flutter_libs`), `webview_flutter`
- ディレクトリ構成を用意する(例): `lib/features/home/`, `lib/features/game/`, `lib/features/result/`, `lib/features/library/`, `lib/core/models/`, `lib/core/repositories/`, `assets/mock_data/`
- `analysis_options.yaml`は`flutter create`のデフォルト(`flutter_lints`)のままとし、変更しない
- go_routerでhome/game/result/libraryの4画面分の空のルートだけ定義する

**スコープ外**：画面デザインの作り込み、認証、Supabase接続、WebView実装は一切行わない。

**成功基準**：`flutter run`で起動し、ボトムナビゲーション相当の導線でhome/library間を行き来できる(中身は空でよい)。

### フェーズ1: JSON固定データでの画面表示・画面遷移の確認(home / game 画面)

**やること**
- `assets/mock_data/quizzes.json`に、固定のクイズデータを**5〜10件程度**用意する(spec.md 3.1の`quizzes`テーブル定義に準拠。`embedding`列は`null`のままでよい)。
- `assets/mock_data/youtube_api_mock.json`を新設し、`video_id`をキーに、実際のYouTube Data API `videos.list`のレスポンス形式を模した「再生数・高評価数」のダミーデータを用意する。あわせて`comment_id`をキーにした「コメントのいいね数」ダミーデータもここに含める。**このファイルの構造は、将来フェーズ5で本物のAPIレスポンスに差し替えることを前提に、できるだけ実際のAPIレスポンスの形に似せておくこと。**
- `lib/core/repositories/quiz_repository.dart`に、①`quizzes.json`からクイズ本体を読み込む処理と、②`youtube_api_mock.json`から再生数等を読み込む処理を合成し、1つの`QuizWithLiveStats`のようなモデルにまとめて返す関数を実装する。**この関数のインターフェース(引数・戻り値の型)は、フェーズ5でSupabase/実APIに中身を差し替えても変わらない設計にすること**(呼び出し側の画面コードを変更せずに済むようにするため)。
- ホーム画面：代表コメント(`thumbnail_comment_id`相当、なければ`video_comments`の先頭)・再生数・投稿からの経過年数を表示するブロックをスクロールフィードで表示する。長いコメントは省略表示にする。
- ゲーム画面：上部固定情報(再生数・高評価数・投稿時期・代表ジャンル)と、ヒント一覧(この時点では全て開放済み状態で表示してよい。開閉ロジックはフェーズ3)を表示する。回答ボタンはまだダミー(押したらresult画面に遷移するだけ)でよい。
- リザルト画面：クイズの全情報を表示する簡易版を作る(次の問題へ/ホームに戻る、の導線のみ確認できればよい)。

**スコープ外**：WebViewでの実際の回答判定、ヒント開閉、絞り込み、Drift・Supabase・YouTube APIへの実接続は行わない。

**成功基準**：home→game→result→homeの画面遷移が一通りでき、JSONデータがレイアウト崩れなく表示される。

### フェーズ2: 回答システムの実装(WebViewでのURL追跡・正誤判定)

このプロジェクトの中で最も技術的難度が高い部分。着手前に必ずライブラリの挙動を小さなサンプルで検証してから本実装に進むこと。

**やること**
- `webview_flutter`を使い、spec.md 2.2節の通り、制御外枠(閉じる・戻る・進む・下部ボタン)を持つWebViewウィンドウを実装する。
- `NavigationDelegate`(`onPageFinished`/`onUrlChange`等)でURLを監視し、`watch?v=`を含むURLかどうかで下部ボタンの表示(「PLAY THE VIDEO」⇔「ANSWER」)を切り替える。
- 「ANSWER」タップ時に`controller.currentUrl()`で現在のURLから`video_id`を抽出し、フェーズ1で作った`quiz_repository`のクイズデータと突き合わせて正誤判定する。
- **実機での検証が必須の項目**：WebView内のYouTubeページ遷移が、iOS/Androidのユニバーサルリンクによってネイティブのユーザー既にインストール済みYouTubeアプリを勝手に開いてしまわないか。まずこの検証を最優先で行い、問題が起きる場合はここで一旦立ち止まり、代替設計(例：リンク遷移の握り潰し方、別のWebViewパッケージの検討)を人間に確認すること。
- 回答時にWebViewを閉じる際は動画を確実に停止させる(WebViewの破棄、またはJSで`pause()`実行)。

**スコープ外**：動画の再生完了検知(JS注入によるプレイヤーイベント取得)は今回は行わず、URL到達のみで判定する簡易版とする(以前の相談通り、暫定でよい)。

**成功基準**：実機で「WebView内でYouTubeを検索→該当動画ページに到達→ANSWERボタン→正誤判定→game/result画面に戻る、かつ動画は停止する」の一連が動作する。

### フェーズ3: ヒント開示機構の追加

**やること**
- Drift側に、現在プレイ中のクイズについて「どのヒントが開放済みか」を保持するテーブルを追加する(spec.md確認事項で指摘した、以前あった`show_music_artists`, `show_video_lyrics`等のフラグに相当するもの。1問ずつのプレイに仕様変更されているため、配列ではなく単一のクイズ分の状態として持てばよい)。
- ゲーム画面のヒントごとに開放ボタンを設置し、タップしたらDriftのフラグを更新→UIに反映する。
- アプリを再起動しても、直前にプレイしていたクイズの開放状態が保持されることを確認する。

**成功基準**：ヒントの一部だけを開放した状態でアプリを完全に終了し、再度開いても同じ開放状態から再開できる。

### フェーズ4: 出題時の絞り込み機能の追加(UX確認目的)

**やること**
- ホーム画面上部に、ジャンル・年代・言語のタグ選択UIを実装する(spec.md 2.4節)。
- 絞り込みロジックは、**この時点ではSupabase/DBを使わず、`quiz_repository`内でDartの`.where()`によるJSON配列の単純フィルタとして実装する**。これはあくまでUXの確認が目的であり、本格的な検索基盤ではないことをコード内コメントに明記する。
- フェーズ5でSupabaseのRPC関数(ENUM配列演算子)に置き換える前提で、フィルタ条件の受け渡し方(引数の形)だけはSupabase移行後も変えずに済む形にしておく。

**成功基準**：タグを選択するとホーム画面のフィードが絞り込まれ、選択解除で全件表示に戻る。

### フェーズ5: 仕上げ ― Supabase・YouTube Data APIへの本接続

**やること**
- Supabaseプロジェクトを作成し、`quizzes`/`users`テーブルを作成する(`music_genre`/`video_genre`/`music_languages`のENUM型定義を含む)。RLSポリシーを設定する。
- `quizzes.json`のデータをSupabaseに一括投入する(投入用の一時スクリプトを書き、投入後は削除するか`tool/`配下に残す場合は役割をコメントで明記する)。
- `quiz_repository`の中身を、JSON読み込みから`supabase_flutter`経由の呼び出し(`.rpc()`/`.from()`)に差し替える。**フェーズ1で決めたインターフェースを保っていれば、画面側のコードは変更不要のはず**。ここが崩れる場合は設計の見直しが必要なサインなので、その旨を報告すること。
- YouTube Data APIキーを取得し、Google Cloud ConsoleでAndroidパッケージ名/iOSバンドルIDによる制限をかける。`youtube_api_mock.json`への依存を、実際の`videos.list`呼び出しに差し替える(`video_id`を最大50件までカンマ区切りでまとめて1回のAPI呼び出しにすることでクォータを節約する)。
- フェーズ4の簡易フィルタを、SupabaseのRPC関数(ENUM配列の`&&`演算子等)を使った本実装に置き換える。
- 余裕があれば、アーティスト名の表記ゆれ検索用に`pg_trgm`拡張とインデックスを追加する(任意項目)。

**スコープ外**：認証機能、ベクトル検索によるレコメンド、翻訳機能は今回のスコープに含めない。着手したくなった場合は事前に確認すること。

**成功基準**：`assets/mock_data/`への依存を完全に切った状態で、実機上で一連のゲームループ(出題→回答→リザルト→ヒント開放→絞り込み)がすべて実データで動作する。
