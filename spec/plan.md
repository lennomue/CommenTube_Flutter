# 開発の計画

## 1. 事前情報
- `spec.md`
  現在の実装と確定仕様だけを記す唯一の正本です。仕様を変更したら古い説明を併記せず、現在形へ更新します。モック期間のデータ元がJSONであることも`spec.md`内に含めるため、旧`spec_mock.md`は2026-09-21に削除しました。

- `game_images`
  ゲームの画面構成の外観を画像で示す。基本的な画面構成はspec.mdに基づく。設計はできだけシンプルが良い。画像に示すような適度な光や影、透明感や立体感の実装は後回し。見た目のデザインよりも挙動、機能面のデザインを優先して実装すること。もしどうしても画像が必要な場合はassets/imagesフォルダなどを追加してください。画像の生成は禁止。追加する画像のサイズなどの条件の指示を出してください。

- `plan.md`
  開発の順番、当時の依頼、変更理由、完了状況、残作業を時系列で残す進行メモです。古いフェーズ内の変数名や案は経緯として残る場合がありますが、現行仕様の判断には必ず`spec.md`を使います。より良い道筋や変更案はここへ理由とともに追記します。
  
- `_commit.md`
  コミットする毎に変更点を書き加える。コミットのタイミングはplan.mdの作業が一区切りしたタイミングでお願いします。planに基づく説明でも、計画自体に変更点があればそれも含めて書きましょう。

## 2. 開発の進行
- 前提や実装に際しての技術的課題に不明点があればわかったふりをすることなく確認すること。
- 実装に際して世の中ですでに使われているライブラリや設計方法を使い回すことができるかを調べ、それを実装すること。すでに`spec.md`にある計画でも、良い設計があれ積極的に変更して良いので提案すること。
- 開発初期にjsonデータで実装する時はその時点で必要最適源の簡潔なデータのみを扱うこと。
- コードを書く際には余計な実装をしないこと。もし進めたいことがあるならば事前に確認すること。
- コードの中で不要なものは消すこと。消さないならば残している理由（役割）をファイルの中にコメントなどで書くこと。
- 仕様変更やフェーズ完了の区切りで、未参照コード、重複文書、実験ファイル、秘密情報を含むキャッシュ、不要な直接依存を監査する。生成物や移行コードは、現在も必要な理由が確認できる場合だけ残す。
- GitHubに更新版をpushする際には変更内容を簡潔な箇条書きで`_commit.md`に加筆すること。
- CI/CDに注意して適切なテストができると良い。環境として容量が小さい現在のmacではFlutter SDKでコンパイルし、実機スマホに繋いでアプリのテストを行う。そのためAIエージェントがテストを行うのは難しいかもしれない。
- 開発の際にはコミットとセットでpushもしちゃってください。

## 3. 開発フェーズ

各フェーズの終わりには、そのフェーズの「成功基準」を満たしているかを確認してからコミットし、`_commit.md`に変更点を加筆する。AIエージェントはFlutterアプリを実機で動かして目視確認することができないため、実機での動作確認が必要な項目は人間が確認し、その結果をエージェントにフィードバックする運用とする。

### フェーズ2: 回答システムの実装(WebViewでのURL追跡・正誤判定)

このプロジェクトの中で最も技術的難度が高い部分。着手前に必ずライブラリの挙動を小さなサンプルで検証してから本実装に進むこと。

**やること**
- `webview_flutter`を使い、spec.md 2.2節の通り、制御外枠(閉じる・戻る・進む・下部ボタン)を持つWebViewウィンドウを実装する。
- `NavigationDelegate`(`onPageFinished`/`onUrlChange`等)でURLを監視し、`watch?v=`を含むURLかどうかで下部ボタンの表示(「PLAY THE VIDEO」⇔「ANSWER」)を切り替える。
- 「ANSWER」タップ時に`controller.currentUrl()`で現在のURLから`video_id`を抽出し、フェーズ1で作った`quiz_repository`のクイズデータと突き合わせて正誤判定する。
- **実機での検証が必須の項目**：WebView内のYouTubeページ遷移が、iOS/Androidのユニバーサルリンクによってネイティブのユーザー既にインストール済みYouTubeアプリを勝手に開いてしまわないか。まずこの検証を最優先で行い、問題が起きる場合はここで一旦立ち止まり、代替設計(例：リンク遷移の握り潰し方、別のWebViewパッケージの検討)を人間に確認すること。
- 回答時にWebViewを閉じる際は動画を確実に停止させる(WebViewの破棄、またはJSで`pause()`実行)。

**スコープ外**：動画の再生完了検知(JS注入によるプレイヤーイベント取得)は今回は行わず、URL到達のみで判定する簡易版とする(以前の相談通り、暫定でよい)。

**成功基準**：実機で「WebView内でYouTubeを検索→該当動画ページに到達→ANSWERボタン→正誤判定→game/result画面に戻る、かつ動画は停止する」の一連が動作する。

### フェーズ5.1: ここまでで発生した新しい課題

**やること**
- homeとlibraryにいるとき画面下部にホームとライブラリを移動できるボタンある。まず高さを今の半分程度にしてください。また選択されたことがときの変化はロゴが白で塗り潰されるだけにしましょう。もし開発に置いてロゴは自作することが良いのならばpngで良ければ透過画像をこちらで用意するので、サイズや画像をおくべきフォルダを伝えてください。
- game画面について、回答の丸い浮遊オブジェクトができています。しかしこれが小さくなった時に左下にずれるのですが、これは真下に下がるのが自然です。
- result画面にてsong_titleが一番上に書かれます。そのすぐ下に小さな字でアーティスト名があり、その下にアーティストの名前が書かれたブロック(お気に入りに追加)があります。ここには複数のアーティストを持つ動画であれば複数を表現します。そのため、長すぎるケースではスライドできるようにしましょう。
- libraryから開く元動画の詳細画面について、result画面の中身を再利用できるならそうしてください。
- アーティスト画面について非常によくできていますが、クイズ画面について曲名は消してコメントだけにしてください。また「このアーティストのクイズを始める」時には、このアーティストの全ての曲が終わったのならば「NEXT QUIZ」ではなく「FINISH」というボタンを押しましょう。

- game画面とresult画面の表示または他画面との遷移の仕方について大きな改修をします。今はどちらも左上にホームに戻るロゴがあります。しかしゲームを開始する場所というのはhomeだけではないのです。library画面やそこから開くアーティスト画面を起点としてゲームが始まります。ゲーム体験が直感的に自然なものになるためには次のような仕様にしましょう。まず前提としてユーザーからみて一番下(裏)はhomeまたはlibraryのどちらか。ユーザーはその上にアーティストページを何枚でも重ねて開くことができるが、この時フッター(homeとlibraryに飛べるもの)を残し、それが押されたら全てのアーティストページを消す。この重なるアーティストページは左上の戻るボタンや左端からのスライドによって一番上(手前)のアーティストページを閉じる。
また逆にアーティストページは必ずhome、libraryの上に複数重なるだけである。言い換えればgame、resultの上には作らない。gameやresultは常に一番手前のレイヤーであるし、複数重なることはない。そしてこのgameとresultはヒントより上のあたりから下にスワイプした時に画面が縮み、丸い浮遊物の記号のオブジェクトに変化します(これも常に一番上のレイヤー)。この浮遊物オブジェクトがクリックされたらそのgameまたはresultのページに戻ってください。
これによって、新しい機能が追加できます。result画面(もといlibraryから開く楽曲詳細情報)にて、アーティストをお気に入りに入れるボタンと別に、元々はmusic_titleのすぐ下に小さく表示されていたアーティスト名があります。これをクリックするとアーティストページに飛ぶようにしましょう。result画面からであればそれを浮遊物オブジェクトに変化させて閉じることで、新しいアーティストページを開いて、その上に丸い浮遊物が残るようになります。libraryから開く楽曲詳細情報からならばシンプルに楽曲詳細情報を閉じて、library画面の上にアーティストページを開きます。


**成功基準**：画面の表示が計画に沿って良くなること。spec.mdも必要な修正が入り、最新の設計だけが見れるように、過去の設計で紛らわしい箇所は消すこと。テストで自然な体験ができることを確認。
