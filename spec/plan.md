# 開発の計画

## 1. 事前情報
- `spec.md`,`spec_mock.md`
  ゲームの実装要件。一部データ型の設計などの細かい計画はデータベースとの相性などを考慮して適宜変更の提案をすること。ゲームの進行や通信のタイミングの設計についても改善の余地があれば提案してください。今の計画書にある骨格のコンセプトやゲームのユーザーの操作手順は変えずに、それを達成するための技術的な選定についてはより良い選択肢があれば変更してほしい。mock版はバックエンドサーバーを立てずに行う。

- `game_images`
  ゲームの画面構成の外観を画像で示す。基本的な画面構成はspec.mdに基づく。設計はできだけシンプルが良い。画像に示すような適度な光や影、透明感や立体感の実装は後回し。見た目のデザインよりも挙動、機能面のデザインを優先して実装すること。もしどうしても画像が必要な場合はassets/imagesフォルダなどを追加してください。画像の生成はお願いしません。追加する画像のサイズなどの条件の指示を出してください。

- `plan.md`
  現状での計画への理解が書かれている。当然より良い開発の道筋や変更すべき点があれば積極的に指摘してほしい。またデータベースの設計についてはあなたが触れる環境の中解決しないものがあるだろうと思われる。その際にはその計画を実行するための手順を詳しく示してください。
  
- `_commit.md`
  コミットする毎に変更点を書き加える。コミットのタイミングはこちらから指示をするので、作業が一区切りしたタイミングで前回書いた時からの変更点を簡潔にAIが加筆する。

## 2. 開発の進行
- 前提や実装に際しての技術的課題に不明点があればわかったふりをすることなく確認すること。
- 実装に際して世の中ですでに使われているライブラリや設計方法を使い回すことができるかを調べ、それを実装すること。すでに`spec.md`にある計画でも、良い設計があれ積極的に変更して良いので提案すること。特にテストの段階でjsonデータで実験をする時はその時点で必要最適源の簡潔なデータのみを扱うこと。
- コードを書く際には余計な実装をしないこと。もし進めたいことがあるならば事前に確認すること。
- コードの中で不要なものは消すこと。消さないならば残している理由（役割）をファイルの中にコメントなどで書くこと。
- GitHubに更新版をpushする際には変更内容を簡潔な箇条書きで`_commit.md`に加筆すること。
- CI/CDに注意して適切なテストができると良い。環境として容量が小さい現在のmacではFlutter SDKでコンパイルし、実機スマホに繋いでアプリのテストを行う。そのためAIエージェントがテストを行うのは難しいかもしれない。

### MVP計画書（PRD: Product Requirement Document）

#### 1. 解決する課題と今取り組む理由

* **課題**: CommenTubeのバックエンドとの通信の実装は負荷が高い。まずはゲームループの検証に専念
* **理由**: コアとなる「クイズ体験」と「WebViewでの正解判定」が技術的・体験的に成立するかを最小コストで迅速に検証するため。

#### 2. 成功基準（Success Criteria）

* 手元（ローカル）に用意した5問のダミーデータで、ヒント解放（ポイント消費）からWebViewでの動画回答、正誤判定、リザルト表示までの一連のゲームサイクルがスマホ上で円滑に動作すること。

#### 3. スコープ（Scope）

* **In（やる事）**:
* Flutter単体での基本UI（ホーム、クイズ、WebView回答、リザルト）の構築
* ローカルのダミーJSONデータ読み込み
* WebView内でのURL監視および動画ID（`watch?v=`）抽出による正誤判定
* メモリ上またはシンプルな状態管理でのCポイント消費・回復ロジック


* **Out（今回はやらない事）**:
* Goバックエンドサーバーの構築・通信
* Supabase / Firebase 認証およびデータベース連携

#### 4. 制約・依存関係・エッジケース（Constraints & Edge Cases）

* **WebViewの制約**: スマホのOS（iOS/Android）によるWebViewの挙動差異や、YouTube側の仕様変更によるURL構造の変化。
* **エッジケース**: `watch?v=` を含まないページ（YouTubeトップやShorts動画）で「回答する」が押された際の例外処理。

#### 5. 構築プランとステップ（Build Plan）

1. **Phase 1（UIの一部を設計）**: Flutterでホーム画面とゲームプレイ画面を作成、jsonデータから表示。
2. **Phase 2（UI・WebView検証）**: ゲームプレイ画面に回答ボタンを追加し、WebViewを構築。動画再生時の回答ロジック+正誤判定をテストする。
3. **Phase 3（コアゲームループ実装）**: 一部ヒントを隠し、ヒント開示ロジックとCポイントの増減を実装。ヒント開示の際のアニメーションなども実装したい。ユーザー体験には重要なフェーズ
4. **Phase 4（お気に入りと設定画面の実装）** お気に入りに追加する機能と、分類のロジックを検証。設定画面も仮で作る(クラウドDBの実装はここではないため)

## 4. 開発-2
**Go言語での開発効率とクエリ性能を両立させるため、まずはSupabase（PostgreSQL）のSQLエディタ上で `EXPLAIN ANALYZE` を用いてデータベース設計とインデックスの検証を行う。最適化されたクエリ構造を確定させた後にGoバックエンドへ移植する方針を推奨します。**

以下に、提示いただいた設計仕様（spec.md）と年代検索の要件に基づいたデータベース設計の方針、および本検証に向けたプロダクト計画書（PRD）を提示します。

---

### データベース設計方針と理由

#### 1. 年代検索（`music_released_at`）の型とインデックス設計

* **方針**: `TIMESTAMPTZ`（タイムゾーン付きタイムスタンプ型）を採用し、**B-tree複合インデックス**を配置します。
* **理由**:
「年月レベルでの厳密な範囲指定（例：2000年4月〜2005年3月）」および「大まかな提案設定（例：2000年代）」の双方に対応するには、日付の範囲検索（`BETWEEN` や `>=` `<`）に最も強いB-treeインデックスが必須となります。
具体的には、頻繁に同時指定される `video_genre`（完全一致）と `music_released_at`（範囲指定）を組み合わせた **複合インデックス（`video_genre`, `music_released_at`）** を作成するのが最も効率的です。

#### 2. 多角的なタグ・属性検索（`music_artists`, `music_languages`）

* **方針**: 配列型（`text[]`）を維持し、**GIN（Generalized Inverted Index）インデックス**を設定します。
* **理由**:
1つの楽曲に複数のアーティストや言語が紐付く仕様において、中間テーブル（多対多の関連テーブル）を作成すると、検索時に `JOIN` コストが発生します。PostgreSQLの `text[]` と GIN インデックスの組み合わせは、配列の包含演算子（`@>`）を用いた検索を劇的に高速化するため、今回のような読み込み主体のクイズアプリには最適です。

#### 3. 既出問題の除外（`quiz_history`）とランダム抽出のアンチパターン回避

* **方針**: `ORDER BY random()` の使用を避け、**Primary Key（`video_id`）の配列比較またはサブクエリによる除外**を行います。
* **理由**:
数万件のデータに対して `ORDER BY random()` を実行すると、全件ソートが発生してパフォーマンスが崩壊します。ユーザーの `quiz_history`（配列）に含まれない ID からランダムに5件を抽出するロジックは、SQLの実行計画を見ながら慎重に設計する必要があります。

---

### PRD: データベース設計・クエリ検証フェーズ

#### 1. 解決する課題と目的 (Problem & Why It Matters)

* **課題**: 多角的な絞り込み（ジャンル、年月範囲、言語）および既出除外を伴うクイズ抽出において、データ量増加時にデータベースのレスポンスが遅延するリスク。
* **目的**: 本実装（Goコード記述）に入る前に、Supabase上で最小構成のテーブルとインデックスを構築し、10万件スケールでも50ms以下で応答する最適クエリを確立すること。

#### 2. 成功基準 (Success Criteria)

* 10万件の疑似データに対し、「ジャンル指定 ＋ 年月範囲指定（例: 2000-01〜2005-12）＋ 言語指定 ＋ 履歴100件除外」の条件下でランダム5件を抽出するクエリの実行時間（`EXPLAIN ANALYZE` の Total Execution Time）が **50ms 以内** であること。

#### 3. スコープ (Scope)

* **In（実施すること）**:
* Supabase上での `quizzes` テーブル作成とインデックス定義（B-tree, GIN）。
* 10万件の疑似データを投入するSQL（または軽量スクリプト）の作成。
* `EXPLAIN ANALYZE` を用いたクエリ実行計画の比較・検証。
* 検証済みクエリのGo言語（`database/sql` や `pgx`）への組み込み。


* **Out（実施しないこと）**:
* Flutterアプリとの通信。
* 認証機能（Supabase Auth）やCポイント同期処理の実装。



#### 4. 制約・依存関係・エッジケース (Constraints, Dependencies, Edge Cases)

* **制約**: Supabaseの無料枠（CPU/メモリ制限）内で十分なパフォーマンスが出ること。
* **エッジケース**: ユーザーの検索条件が狭すぎて、該当する問題が5件未満（または0件）しか存在しない場合のクエリ挙動。

#### 5. 構築プラン (Build Plan)

1. **Phase 1（Supabaseでの直接検証）**:
* SQLエディタでテーブルとインデックスを作成。
* 疑似データ30件を生成・投入。
* 条件絞り込みクエリの実行計画（`EXPLAIN ANALYZE`）を確認し、インデックスが正常に使われているか（Index Scan）を検証。

2. **Phase 2（Goバックエンドへの接続・移植）**:
* 検証完了したSQLクエリをGoのコードに組み込み、GoからSupabaseへ接続してレスポンス速度とメモリ消費量を計測。
